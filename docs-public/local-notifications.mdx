---
title: "Local notifications"
description: "Schedule notifications on the device with no Notifie account, no API key and no network."
---

Local notifications are scheduled and presented by the operating system on one
device. They need no API key, no network and no Notifie account — a reminder app
can ship without a backend.

This is the same SDK you later connect to Notifie Cloud. Adopting Cloud adds
identity, durable queues and workflows; it does not replace these APIs or
require a second integration.

<Note>
Local notifications work offline. Turn on airplane mode, schedule one, and
background the app — it still arrives.
</Note>

## Schedule

<CodeGroup>

```swift Swift
import Notifie

let result = await Notifie.schedule(
    LocalNotification(
        id: "daily-practice",
        title: "Time to practise",
        body: "Your streak is waiting.",
        schedule: .daily(hour: 9, minute: 0),
        deepLink: "myapp://practice"
    )
)
```

```kotlin Android
import dev.notifie.*

val result = Notifie.schedule(
    context,
    LocalNotification(
        id = "daily-practice",
        title = "Time to practise",
        body = "Your streak is waiting.",
        schedule = LocalSchedule.Daily(hour = 9, minute = 0),
        deepLink = "myapp://practice",
    ),
)
```

Kotlin imports packages rather than modules. All Android SDK types live in
`dev.notifie`, so the single wildcard import is the Android equivalent of
Swift's `import Notifie`.

```dart Flutter
import 'package:notifie_flutter/notifie_flutter.dart';

final result = await Notifie.schedule(
  const LocalNotification(
    id: 'daily-practice',
    title: 'Time to practise',
    body: 'Your streak is waiting.',
    schedule: LocalScheduleDaily(hour: 9, minute: 0),
    deepLink: 'myapp://practice',
  ),
);
```

</CodeGroup>

## Schedule kinds

| Kind | Fires |
| --- | --- |
| `at` | Once at an absolute instant |
| `after` | Once after an interval |
| `daily` | Every day at a wall-clock time |
| `weekly` | Every week at a wall-clock time |

Weekdays follow ISO-8601: **Monday is 1, Sunday is 7.**

Recurring schedules repeat on wall-clock components, so a 9am reminder stays at
9am across a daylight-saving change rather than drifting an hour and staying
there.

Monthly recurrence is deliberately unsupported. "The 31st of every month" has no
correct answer in February, and every available behaviour surprises somebody
silently. Use a sequence of `at` schedules to say exactly what you mean.

## Replace and cancel

Identifiers are yours and stable. Scheduling an id that is already pending
**replaces** it rather than adding a second notification, so re-asserting a
reminder on every launch is safe.

<CodeGroup>

```swift Swift
Notifie.cancelScheduled(id: "daily-practice")
let pending = await Notifie.pendingScheduled()
```

```kotlin Android
Notifie.cancelScheduled(context, "daily-practice")
val pending = Notifie.pendingScheduled(context)
```

```dart Flutter
await Notifie.cancelScheduled('daily-practice');
final pending = await Notifie.pendingScheduled();
```

</CodeGroup>

Cancelling an id that was never scheduled is harmless, so cancellation is safe
to call defensively.

`pendingScheduled` returns only notifications this SDK scheduled. Cloud
notifications and any your app scheduled directly are excluded, because
reporting them would imply an ownership the SDK does not have.

## Permission

Request permission **in product context**, not at launch. iOS shows the prompt
once per install, so a denial is effectively permanent. Asking when someone has
just chosen a reminder is the difference between a granted permission and a lost
one.

## Errors

Failures are distinguished because each needs a different response.

| Error | Meaning |
| --- | --- |
| `permission_denied` | Notifications are denied. Ask the user to change Settings. |
| `capacity_exceeded` | iOS holds only 64 pending notifications per app. |
| `schedule_in_past` | The requested time has already passed. |
| `invalid_request` | Content or schedule failed validation. |
| `platform_error` | The platform rejected the request for another reason. |

## Platform differences

<Tabs>
  <Tab title="iOS">
    iOS keeps only the **64 soonest** pending notifications and silently
    discards the rest. Notifie reports this as `capacity_exceeded` rather than
    letting a reminder vanish. Verified on an iPhone: the 65th request is
    rejected, not dropped.

    **Request permission before scheduling.** Until permission is granted, iOS
    accepts a scheduled request and then keeps nothing — `pendingScheduled`
    returns empty and the notification never fires. Notifie cannot detect this,
    because the platform reports success either way.

    Scheduling precision is not separately permissioned, so a scheduled
    notification is as exact as the platform offers.
  </Tab>
  <Tab title="Android">
    Inexact alarms are the default. Exact alarms are a scarce system resource
    and need a user-visible permission on Android 12+, so requesting one may be
    **downgraded rather than granted**.

    Always read the granted precision instead of assuming:

    ```kotlin
    when (val result = Notifie.schedule(context, notification)) {
        is LocalScheduleResult.Scheduled -> log("granted ${result.precision}")
        is LocalScheduleResult.Failed -> log("failed ${result.error}")
    }
    ```

    Schedules are persisted and re-armed after a reboot or an app upgrade,
    because `AlarmManager` keeps nothing across either.

    Restoration happens **after the device is first unlocked**, not at boot.
    Android keeps app storage credential-encrypted until unlock, so the stored
    schedules are literally unreadable before then. A reminder due between boot
    and first unlock is delivered late, once restoration runs. This is verified
    behaviour on a Pixel, not a theoretical limit.

    Battery optimisation and OEM background restrictions can delay inexact
    alarms. That is a platform constraint, not a reliability guarantee Notifie
    can make.
  </Tab>
  <Tab title="Flutter">
    Flutter delegates to the native iOS and Android implementations rather than
    scheduling in Dart, so behaviour matches the native SDKs exactly.

    Query what the current device supports before relying on it:

    ```dart
    final capabilities = await Notifie.notificationCapabilities();
    if (!capabilities.canScheduleExactAlarms) {
      // Degrade rather than promise precision the device will not deliver.
    }
    ```
  </Tab>
</Tabs>

## Deep links

A `deepLink` is delivered to your notification-open handler. Notifie never opens
it: routing is the app's decision, and a URL that opens itself is a URL you
cannot intercept, validate or defer.

Local notifications use the same open handler as Cloud push, so one integration
handles both.
